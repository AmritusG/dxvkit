# Clean-room questions (Phase B)

Questions the Phase B session (W2, 2026-10-08) met while implementing from `docs/spec/`. Per the
protocol each was settled from the spec and the test vectors only (no upstream code), and the method
is recorded. Items marked **for Phase A** are relayed by Cowork; none of them blocks the decoder.

| # | Question | Settled how | Status |
|---|---|---|---|
| 1 | The W1 results handoff says that with 16x16 padding "every Resolume stream uses every opcode and every literal exactly". Spec 7.5 says Resolume "occasionally" leaves one dangling opcode (one 480x360 clip). Which is it for the vectors? | Measured with the decoder's consumption report (`dxvtool check`) and a scratch debug build: all 4 Resolume **YCG6** vector frames (Alley 0..2, AME 0) leave exactly **one opcode 3 (literal block) plus its 8 literal bytes** unused at the end of the **Y** channel, after a run that already completed the plane (repeat counter 0, all FSE streams still leave exactly 32 bits). YG10, DXT1, DXT5 vectors and both chroma channels are exact. So it is not "occasionally" a single clip: it is every YCG6 frame in the vectors, and on real Resolume YCG6 clips 6,571 of 6,650 frames (KLV "01_AWAKE"), 6,716 of 6,716 (the 480x360 clip) and 121 of 121 (908x2276) carry such a tail, while one 512x1280 clip has none; there the dangling opcodes are not always opcode 3 (121 opcodes, 503 literal bytes), but their literal bytes always equal the unread literal area exactly. No YG10, DXT1 or DXT5 file has any slack. The decoder ignores it, as spec 7.5 says, and the report separates "exact apart from a dangling tail" (literals unused = literals the dangling opcodes would read) from real slack. | Settled (decoder). **For Phase A:** correct finding 2 of the W1 handoff / sharpen spec 7.5 ("Resolume YCG6: one dangling opcode per frame in the Y channel"). |
| 2 | FSE spread step: the spec (7.3.2) says 641; the public FSE descriptions use (size/2 + size/8 + 3) = 643 for a 1024-state table. Is 641 a typo? | Experiment on the vectors: with 641 all 8 Resolume HQ rows match byte for byte and every FSE stream leaves exactly 32 bits; with 643 all 8 rows fail (back-reference before start / empty dictionary slot). 641 is right. | Settled: 641. |
| 3 | Opcode-stream selector 3 (spec 7.3: "2 or 3 = entropy-coded"): is it the same coding as 2? | The vectors contain only selector 2 (28 Resolume streams) and 0 / 1 (98 GlEnc streams); selector 3 never occurs. The decoder treats 3 exactly like 2, as the spec says. Unverifiable from the vectors. | Open, harmless. **For Phase A:** confirm selector 3 is never written / means the same. |
| 4 | Literal reads past the opcode-area offset: spec 7.5 says SHOULD reject (MUST only past the payload). Strict or lenient? | Strict (reject past the opcode-area offset). All 102 vector packets and the 20 real files decode under the strict rule (W2 results). | Settled (strict). |
| 5 | DXV3 stored flag on YCG6 / YG10: undefined (spec 3.3, SHOULD reject). | Rejected with `DXVK_ERR_UNSUPPORTED`. No vector or real file has it. | Settled by the spec. |
| 6 | Sample-entry FourCCs other than `DXD3` / `DXDI` (spec 2.2: MAY accept). | Not accepted: `DXT1` / `DXT5` as a container FourCC could be another codec. Never observed (INVENTORY.md). | Design choice. |
| 7 | Premultiply conversion formula (brief 1.c asks for a straight -> premultiplied option; the spec defines none). | c' = (c x a + 127) / 255 (round to nearest), colour channels only, alpha variants only, RGBA path only. Default stays "untouched" (spec 8.5). | Design choice. Whether Arena treats Alley (straight) and AME (premultiplied-looking) files differently is still Amrit's open question from W1. |
| 8 | Largest frame size. The spec stops at "unobserved above 16384". | `DXVK_MAX_DIMENSION` = 16384 per axis (also the Apple GPU texture limit). | Design choice. |
| 9 | Count extensions (spec 6.4) have no upper bound. | Counts are size_t and clamped to the texture end (block run) or simply count down (alpha run, HQ repeat); every extension u16 is bounds-checked, so the payload length bounds the work. | Settled. |

## W3 (encoder, clean room, 2026-10-08)

Questions the W3 encoder session met. Settled only from the spec, our decoder, the vectors and black-box
runs of the ffmpeg / ffprobe 8.1.1 binaries (Homebrew) and Resolume Arena 7.28 (files loaded, thumbnails
read, nothing triggered). No source code of any DXV implementation was read.

| # | Question | Settled how | Status |
|---|---|---|---|
| 10 | BC3 colour halves: spec 8.2 says they always decode four-colour, so endpoint order should not matter. Does every decoder agree? | Black box: ffmpeg decodes a BC3 colour half with c0 <= c1 as **three-colour** (BC1 rule). Our first DXT5 encode left c0 <= c1 in some blocks: 39,023 of 294,372 RGBA bytes differed by more than 2 at 333x221; after ordering every BC3 colour half like four-colour BC1 (c0 > c1, or c0 = c1 with only index 0) the remaining differences were all explained by item 11. Encoder change: BC3 colour halves are always ordered c0 > c1. Valid for every decoder that follows the spec, and safe for decoders that apply the BC1 rule. | Settled (encoder). **For Phase A:** add to spec 8.2 that encoders should order BC3 colour endpoints c0 > c1. |
| 11 | What does ffmpeg output for DXT5? | Black box: ffmpeg's RGBA for DXT5 is our decoded colour **un-premultiplied**: floor(c x 255 / a), clamped (145,012 of 145,971 channel values with 0 < a < 255 exact, the rest +-1..2 from BC1 rounding); alpha identical. So ffmpeg treats DXV DXT5 as premultiplied alpha. YG10 through ffmpeg comes out as yuva420p planes, untouched. `dxvtool cmp-rgba --unpremultiply-b` reproduces this for the oracle. | Measured. Relevant to the open straight-vs-premultiplied question (spec 10.5): **for Amrit / Phase A**. DXVKit keeps writing what the caller gives (straight by default, like Alley). |
| 12 | Does ffmpeg size the texture like Resolume (16 x 16 padding, spec 2.3)? | Black box: no. ffmpeg 8.1.1 rounds the **width to 4**: it decodes a 908-wide stream as 227 blocks per row (our 908x2276 DXT1 re-indexed at 227 blocks per row matches ffmpeg's output on every pixel within +-1; at 228 it does not), and it mis-decodes Resolume's own 908x2276 DXT1 file the same way (5,765,047 of 8,266,432 RGBA bytes wrong, no warning). It rejects our 18x10 HQ / DXT1-1x1 files ("Invalid data"). Where ceil4(W) = ceil16(W) (16x16, 333x221, 1920x1080, 3840x2160) it decodes our files without warnings and matches. Arena decodes our 908x2276 DXT1 / YCG6, 333x221 YG10 and 18x10 DXT5 files correctly (thumbnails). | Settled: our files follow Resolume (16 x 16). ffmpeg is a reference only where ceil4(W) = ceil16(W); `tools/oracle.sh` reports the other sizes as "ffmpeg geometry". |
| 13 | ffmpeg's BC1 rounding convention (brief: "say which"). | Black box: DXT1 RGBA differs from ours by at most 1 per channel in 0.6 % of bytes at 1080p. No single closed form among 12 tried (bit replication / multiply-round / multiply-truncate expansion x truncating / rounding thirds and halves) matches every pixel; the closest, multiply-round expansion ((v x 255 + 15) / 31, (v x 255 + 31) / 63) with truncating thirds, matches 98.9 %. Ours is the spec's (bit replication, truncating integer interpolation, spec 8.1). | Characterised (+-1). Not pursued further: reading ffmpeg's source is not allowed. |
| 14 | Does Resolume play DXV3 stored-flag packets (notes 2, open)? | Arena 7.28 opens DXT1 and DXT5 stored-flag files (`--stored-payload`) and renders correct thumbnails. Live playback not checked (no triggering in this session). | Partly settled. Option stays off by default. **Amrit:** fire columns 9 / 10 of layer "DXVKit Encoder" to confirm playback. |
| 15 | Padding content: notes 3 suggests flat black; the W3 brief says edge replication. | Brief followed: edge replication (cheap: replicated rows / columns become repeats; better BCn at the picture edge). | Design choice. |
| 16 | `DXVK_ENC_PREMULTIPLIED_INPUT` (brief: "an option says the input is premultiplied and is written as such"): what should it change? | The file has no field for the convention and the encoder never converts, so the bytes are the same either way; the flag records the caller's convention (exposed in C, C++, Swift). | Design choice. |
| 17 | FSE with a single opcode value (spec 10.8). | Not writable: the first count is read with width 10, so a count of 1024 does not fit. The encoder uses fill for one value, and FSE only when it is smaller than stored. | Settled by the spec's own width rule. |
| 18 | Resolume's dangling HQ opcode (item 1). | Not reproduced: opcode counts are exactly the opcodes needed, every literal is read, FSE streams leave 32 bits (`dxvtool check`: 0 inexact, 0 dangling tails on every encoder output). | Settled (encoder). |
| 19 | Default opcode coding (brief: "whichever matches Alley's size better"). | Alley writes FSE streams (28 / 28 in the vectors). `auto` (cheapest of FSE / stored / fill per stream) lands within 5 % of Alley's packet sizes on the testsrc2 frames; `stored` is 15 % (YCG6) and 29 % (YG10) larger on the same frames (W3 results handoff). Default = `auto`. | Settled. |
| 20 | The testsrc2 source of the `resolume` vectors is not in the repo (`test_vectors/source` holds only our pattern). | Reconstructed by experiment: ffmpeg `testsrc2` (yuv420p) converted with the BT.709 limited-range matrix and bilinear chroma, alpha = 255 for x < 640, 128 for x < 1280, else floor(255 x / 1920) (the alpha matches Alley's YG10 alpha exactly). RGB matches Alley's decoded output at only 33-34 dB, because testsrc2's random-noise squares and the chroma filtering differ. PSNR against this source therefore favours us; the packer comparison (same blocks) does not depend on it. | Approximate. **For Amrit:** an Alley export of our exact source would give a fair quality comparison (handoff). |
| 21 | Fair quality comparison with Alley (follow-up to 20). | Amrit exported our exact source (`out/w3/dxvkit-w3_alley-source_testsrc2_1920x1080_qtrle.mov`, lossless) through Alley 7.28; both encoders measured against the same RGBA (frames 0-2). DXT1: Alley 98,973 B / 39.71 dB, ours fast 99,080 / 39.70, best 100,027 / 39.88. DXT5: Alley 192,394 / 39.71, ours fast 190,352 / 39.70, best 177,876 / 39.86 (alpha lossless in all). YCG6: Alley 132,032 / 37.71, ours fast 123,400 / 37.95, best 123,218 / 38.03. YG10 export missing (the "HQ with alpha" file is a YCG6 copy). | Settled for DXT1 / DXT5 / YCG6: parity or better. The +4..+6 % in the W3 results handoff came from the reconstructed source. |
| 22 | Fair comparison, complete set (follow-up to 21). | Amrit re-exported all four variants from the same lossless source with correct names (`out/w3/*_qtrle_{Normal Quality No Alpha, DXV Normal Quality With Alpha, High Quality No Alpha_Custom, High Quality With Alpha}.mov`; DXT1 / DXT5 / YCG6 byte-identical in size to the first export). YG10: Alley 215,546 B / 37.71 dB, ours fast 207,406 / 37.95, best 207,224 / 38.03, alpha lossless in all; repack of Alley's YG10 blocks -0.30 %. DXT1 / DXT5 / YCG6 as in item 21. | Settled: parity or better in all four variants. |
